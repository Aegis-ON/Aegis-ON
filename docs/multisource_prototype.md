# 다중 로그 관제 프로토타입과 검증 범위

Aegis-ON은 특정 제품 판별기가 아니라 다양한 보안 로그를 분석가가 검토하는 관제 프로토타입입니다. 경고·점수·명령 모델 결과는 공격 성공이나 악의를 확정하지 않습니다. 승인은 실제 차단이 아닌 시뮬레이션입니다.

## 구현과 연동 계획

| 로그 | 현재 처리 | 제한 및 후속 작업 |
| --- | --- | --- |
| 엔드포인트 Sysmon | 기존 Windows 수집기와 인증된 ID 1/3 정규화, 규칙·명령 모델·외향 목적지 상관 | 실제 Windows, PowerShell, DPAPI, 설정과 재부팅 등 별도 검증 필요 |
| 인증 | `POST /api/v1/ingest/auth`에 전달된 정규화 JSON의 성공·실패를 저장·표시, 배치 간 반복 실패→성공 상관 | 실환경 제품별 어댑터, 권한/계정 변경 이벤트, 다른 로그 간 상관은 미구현 |
| 네트워크 | Sysmon ID 3의 연결 및 외향 다수 목적지 상관 | 방화벽·라우터의 독립 수집, 연결 허용/차단 결과, 포괄적 프로토콜 정규화는 미구현 |
| 웹 | 수집·정규화·탐지 미구현 | 서비스 ID, 시각, 메서드, 경로, 상태코드의 엄격한 필드 허용 목록 필요. 쿼리·본문·쿠키·Authorization은 수집 금지 |

인증 입력은 외부 수집기/어댑터가 원본 로그에서 정규화해 전송하는 형식이며, Windows Security나 특정 서버 로그를 직접 수집한다는 뜻이 아닙니다. 인증→프로세스→네트워크의 교차 로그 연쇄는 미구현입니다. 현재 인증 스키마의 `host`는 수집기가 보고한 값이지 인증 대상 단말의 검증된 자산 ID가 아닙니다. 계정 역시 issuer/realm이 보장된 고유 주체가 아닙니다. 다른 수집기나 PC를 이름 또는 IP가 같다는 이유로 연결하지 않습니다. 인증과 Sysmon을 연결하려면 관리자가 검증한 수집기·대상 자산 매핑, 계정 issuer와 subject 또는 SID, 각 출처의 시간 정확도 계약이 필요합니다. Sysmon 프로세스와 연결의 관계도 동일 자산·프로세스 GUID와 발생 시각을 확인해야 하며, PID나 이름만으로는 확정할 수 없습니다. 관련 근거가 없으면 해당 단계는 연결되지 않습니다.

인증 상관은 **같은 수집기, 보고된 호스트, 정확히 같은 계정 문자열, 정규화한 출발 IP**에서 10분 이내 실패 3건 이상 후 성공이 더 늦은 시각에 기록될 때 검토 경고를 만듭니다. 데이터는 여러 배치와 역순 도착을 지원합니다. 동일 시각은 선후로 취급하지 않습니다. 미지정/멀티캐스트 IP, 빈 값 또는 `unknown`, `n/a`, `-` 계정/호스트는 거부합니다. 이 조건은 같은 실제 인물·장치 또는 공격을 입증하지 않습니다. 공용 NAT/프록시, 관리자 실수, 승인된 점검으로도 경고가 발생할 수 있습니다. 같은 실패 뒤에 성공이 여러 번 기록되면 각 성공에 대해 별도 경고가 만들어질 수 있습니다.

### 인증 입력 예시 — 가상 데이터

수집기별 인증 및 HTTPS/루프백 제한은 기존 수집기와 동일하며 `X-Collector-ID`, `Idempotency-Key`, Bearer 수집기 자격이 필요합니다. 동일 배치 키와 동일 본문은 기존 결과를 반환합니다. 다른 배치의 동일 이벤트는 재집계하지 않으며 신규 이벤트와 섞여도 하나의 트랜잭션에서 신규 부분과 상관 결과를 저장합니다. 같은 이벤트 ID에 다른 내용이나 같은 배치 키에 다른 본문이 오면 전체 배치를 409로 거부합니다. 출처별 안정적인 `event_id`는 어댑터가 보장해야 하며, 수집기가 교체되면 기존 이벤트와 자동 연결되지 않습니다.

```json
{"events":[
  {"event_id":"auth-001","timestamp":"2026-01-01T00:00:00Z","host":"demo-auth-server","account":"demo-user","source_ip":"192.0.2.1","outcome":"failure"},
  {"event_id":"auth-002","timestamp":"2026-01-01T00:01:00Z","host":"demo-auth-server","account":"demo-user","source_ip":"192.0.2.1","outcome":"failure"},
  {"event_id":"auth-003","timestamp":"2026-01-01T00:02:00Z","host":"demo-auth-server","account":"demo-user","source_ip":"192.0.2.1","outcome":"failure"},
  {"event_id":"auth-004","timestamp":"2026-01-01T00:03:00Z","host":"demo-auth-server","account":"demo-user","source_ip":"192.0.2.1","outcome":"success"}
]}
```

필드는 위 여섯 개로 제한합니다. 그 외 필드(비밀번호·토큰·쿠키·쿼리·본문 포함)는 거부하며 예외에 입력 원문을 넣지 않습니다. 계정과 IP 원문은 저장하지 않습니다. 새 인증 레코드 지문과 상관 그룹, 배치 지문은 목적을 구분한 HMAC-SHA-256으로 보관합니다. 표시 그룹은 HMAC 앞 16자리이며 표시용 축약이라 충돌 가능성이 있습니다. 기존 호스트·이벤트 ID의 해시와 PII 탐지에는 여전히 추측·연결 위험이 있습니다. 가명화는 익명화가 아닙니다.

### 비밀키, 마이그레이션과 보존

최초 인증 수집 시 서버는 DB 옆 `<DB 경로>.correlation-key`에 임의의 32바이트 키를 생성하고 DB에는 키 확인값만 저장합니다. POSIX에서는 파일 권한 0600을 확인합니다. 키 파일과 DB를 함께 비공개로 백업·복구하세요. 같은 디렉터리에 두 파일이 있으므로 함께 유출되면 분리 보관 효과가 없습니다. 파일을 Git에 넣거나 공유하지 마세요. 키가 사라지거나 바뀌면 기존 그룹과 섞지 않도록 신규 인증 수집을 503으로 중단합니다. 기존 키를 복원해야 합니다. 자동 키 교체·삭제·새 세대 전환 도구는 제공하지 않습니다. 키 파일 원자적 설치, 파일시스템/권한 동작은 실제 Windows에서 검증하지 않았습니다.

기존 v3 DB의 인증 이벤트는 원문 계정·IP가 이미 없으므로 자동으로 새 상관 인덱스에 들어가지 않습니다. 인증된 수집기가 원본 배치를 동일한 ID·내용으로 재전송하면 동일 배치 키든 다른 배치 키든 검증 후 재색인합니다. 동일 배치 키의 구형 재전송도 재색인 후 replay 응답을 반환합니다. 원본을 다시 받지 못한 과거 이벤트는 상관 불가이며 과거의 무염 지문도 그대로 남습니다. 구형 이벤트의 표시 그룹은 재전송한 배치 이력에만 추가될 수 있어 다른 과거 배치 화면에는 `—`로 표시될 수 있습니다.

상관 상태와 이벤트 식별자는 현재 자동 만료되지 않으며 데이터베이스를 삭제할 때까지 남습니다. 운영용 보존 정책과 안전한 정리 기능은 미구현입니다. 발생 시각 기준으로 과거 또는 미래 이벤트를 받아 역순 도착도 분석하지만, 로그 누락이나 롤오버·시간 오차를 복구하거나 발생 순서를 보장하지 않습니다. 각 변경 시점 전후 20분 조회에 5,000건을 초과하면 전체 배치를 503으로 거부하고 부분 ACK하지 않습니다. 무제한 지연, 처리량과 운영 신뢰성은 검증되지 않았습니다. 승인된 경고에 새로운 근거가 더해지면 이전 승인은 그대로 두고 새 검토 경고를 만듭니다.

## 탐지 방식과 AI

- 규칙·키워드는 기존 프로세스 명령 패턴을 점검하며, 상관분석은 명시적인 조건과 시간 관계를 별도 코드로 처리합니다.
- 공격 분석 AI는 선택적으로 설치한 로컬 BERT-Tiny 이진 모델로 Sysmon 명령줄을 분석합니다. 단일 명령에 대한 분류이며 인증·웹·네트워크 로그나 이벤트 간 시간 관계를 직접 분석하지 않습니다. 결과가 낮다고 안전을 확정하지 않으며 사용 불가·추론 오류도 별도 상태입니다.
- PII 모델은 별도 선택형 로컬 NER이며 공격 모델과 역할이 다릅니다. 인증 어댑터에서는 원문 계정과 IP를 모델에 전달하지 않고 정해진 필드만 정규화합니다. 어떤 PII 모델도 누락 가능성이 있습니다.
- 인증·네트워크·웹 AI를 도입하려면 각 원본별로 필요한 필드, 라벨과 수집·사용 권한을 정의하고, 운영 환경에서 수집·가명처리한 데이터의 출처/시간/템플릿 단위 분리 및 외부 검증이 필요합니다. 예를 들어 인증은 성공/실패와 계정·출발지의 집계, 웹은 쿼리와 본문을 제거한 메서드·경로·상태를 별도 모델의 입력 후보로 검토할 수 있습니다. 시계열 모델을 별도로 학습·검증하기 전에는 시간 순서를 기존 상관분석이 처리합니다. 실제 운영 정보는 외부 모델이나 서비스로 전송하지 않습니다.

### 모델 후보와 실행 결과

[SecRoBERTa](https://huggingface.co/jackaduma/SecRoBERTa)는 보안 텍스트, [CodeBERT](https://huggingface.co/microsoft/codebert-base)는 코드/자연어에 대한 사전학습 모델입니다. 어느 쪽도 별도 분류 학습이나 검증 없이 공격 탐지기로 취급할 수 없습니다. 기존 로더는 BERT 형식과 6개 산출물을 강제하므로 RoBERTa 계열을 채택하려면 토크나이저·설정·모델 무결성 검증을 수정해야 합니다. 이번 환경에서는 해당 후보의 가중치와 동일 훈련 데이터를 확보·학습하지 못해 성능 비교를 실행하지 않았고 우열을 주장하지 않습니다. 기존 선택형 BERT-Tiny를 유지하며 새 모델을 기본으로 채택하지 않았습니다.

기존 보고의 동일 합성 평가 24건에서 기존 BERT는 TP 12 FP 12 TN 0 FN 0, 정밀도 .500 재현율 1.000 F1 .667, 별도 개선 BERT는 TP 7 FP 2 TN 10 FN 5, 정밀도 .778 재현율 .583 F1 .667입니다. 작은 합성 표본, 수작업 그룹, 기존 데이터와 도구 계열 중복 가능성 및 약한 라벨은 [기존 평가 문서](command_refinement.md)에 기록되어 있습니다. 이 수치는 금융기관 운영 성능이 아닙니다.

이번 재실행에서 별도 보관된 개선 BERT(`bff7da13…`)를 로드해 동일 24개 합성 명령에 추론한 결과는 위 개선 BERT의 분류 결과와 같았습니다. macOS arm64, Python 3.12.2, CPU에서 모델 로드 3.445초, warm-up 이후 24개 총 0.025초(평균 1.05ms), 프로세스 최대 RSS 약 336MiB가 측정됐습니다. 단일 실행이며 측정값에는 프레임워크가 포함되고 독립 벤치마크가 아닙니다. 기존 원본 가중치와 후보 모델이 이 환경에 없어 같은 조건으로 재측정하지 못했습니다.

개선 BERT의 합성 오탐은 BitLocker와 프록시 조회 각 1건, 미탐은 프록시 설정 2건, 이벤트 추적 설정 2건, 원격 PowerShell 설정 1건입니다. 승인된 관리자 명령이 탐지될 수 있으며 모델이 모르는 표현이나 맥락에서 의심 행위를 놓칠 수 있습니다.

### 후보 비교 재현 준비

1. 사용 허가를 확인하고 세 후보의 **정확한 revision**, 토크나이저와 모델 가중치를 신뢰할 수 있는 경로로 별도 확보하고 파일별 SHA-256을 기록합니다. SecRoBERTa 모델 카드는 Apache-2.0을 표기합니다. CodeBERT 모델 카드의 라이선스 메타데이터는 확인되지 않아 가중치 사용 조건을 별도로 확인해야 합니다. 이번 평가에서는 후보 가중치를 확보해 학습하지 않았습니다.
2. `evaluation/command_refine_dev_v1.json`(학습 40, 검증 16)과 `evaluation/command_refine_test_v1.json`(평가 24, unknown 3 제외)의 해시·라벨 기준을 확인합니다. 기존 개선 BERT는 이전 학습 이력이 있으므로 새 후보와 동일한 사전 학습 이력의 공정한 비교가 아닙니다. 향후 모든 후보를 각 후보의 사전 고정된 사전학습 revision과 동일한 후속 데이터·학습·평가 조건으로 별도로 학습하고 기존 체크포인트는 참고선으로 나눠야 합니다.
3. 데이터 출처와 가상의 관리자/검토 라벨을 기록하고, 수동 그룹·정규화 일치 및 변형 유사도 후보를 확인합니다. 과거 v2 평가 예제와 개선 학습 예제에 유사 템플릿이 있어 v2를 독립 시험에 사용하지 않습니다. 수작업 그룹과 유사도 점검도 의미 중복이 없다는 보장은 아닙니다. 독립 출처 평가가 추가로 필요합니다.
4. 모든 후보에 동일 seed, 분할, 라벨, 토큰 상한, 임계값 및 CPU 측정 절차를 적용해 분류기를 **실제로 학습**하고 모델·데이터 해시, 정밀도·재현율·F1, 오탐·미탐, 추론 시간·프로세스 메모리를 기록합니다. 현재 저장소의 `command_refine.py`는 BERT 전용이라 SecRoBERTa/CodeBERT를 그대로 평가하지 못하며, 후보별 토크나이저와 학습·평가 하네스를 만들고 검증하는 작업이 남았습니다. 가중치 확보나 하네스 작성만으로 비교 완료라고 볼 수 없습니다.
5. 기존 가중치가 준비된 경우 [기존 비교 명령](command_refinement.md)을 실행하고, 개선 모델 단독 통합은 `AEGIS_ATTACK_INTEGRATION=1 AEGIS_ATTACK_MODEL_DIR=/local/model AEGIS_ATTACK_MODEL_MANIFEST=/local/model/manifest.json PYTHONPATH=src python -m pytest -q tests/test_attack_real_model.py tests/test_real_model_console_optin.py`로 재현합니다. 실제 모델 파일과 로그는 Git에 넣지 마세요.

## ARTEX Global / AntiFox 코드 검토

| 확인한 사실 | 관측 가능성 및 미확인 가설 |
| --- | --- |
| [ARTEX 탐지 문서](https://github.com/jiwoochris/artex-global/blob/main/detections/README.md)는 자산 탐색 요청·요청 속도·다수 대상 접근 및 일반 `curl`/`nmap` 실행을 설명 | 실제 실행 PC의 Sysmon 1/3은 해당 프로세스와 연결을 볼 수 있지만 Docker/VM 내부 실행은 호스트 설정에 따라 보이지 않을 수 있음. 서버 웹/네트워크 로그가 있어야 수신 요청·경로/상태와 서버 관점의 빈도를 볼 수 있음 |
| [AntiFox WebFetch 코드](https://github.com/AntiFox-AI/antifox/blob/main/engine/tool/webfetch.go)는 HTTP(S) GET, 프록시 및 `norma/0.4` User-Agent를 사용하고 [Bash 코드](https://github.com/AntiFox-AI/antifox/blob/main/engine/tool/bash.go)는 셸 명령 실행 기능을 제공 | WebFetch UA는 공유 SDK에서도 쓰여 도구 특정 근거가 아님. Sysmon ID 3만으로 TLS 내부 경로·UA·본문을 볼 수 없음. 요청 경로·상태·인증 결과는 이를 기록한 대상 서버 로그가 있어야 확인 가능 |

다수의 실패/성공과 연결 패턴이 자동화 탐색과 관련될 수 있다는 것은 아직 실험하지 않은 가설이며 정상 관리/감시 작업과 구별해야 합니다. 실행 중인 모델의 계획, TLS 내 요청 내용, 대상 서버의 인증 결과는 현재 Sysmon만으로 확인할 수 없습니다. 두 도구는 실행하지 않았습니다. 각 저장소의 AGPL-3.0과 별도의 사용 조건을 확인하세요. [ARTEX 사용 조건](https://github.com/jiwoochris/artex-global)은 허가된 대상 및 로컬 격리 검증을 명시하고, [AntiFox 사용 조건](https://github.com/AntiFox-AI/antifox)은 학습·코드 연구·로컬 검증 용도 및 온라인 시스템 테스트 금지를 명시합니다.

로컬 서버와 수집기 자격을 설정한 뒤 시연용 가상 인증 이벤트를 한 배치로 전송할 수 있습니다. 이 스크립트는 `127.0.0.1`만 사용하며 실환경 인증 로그를 수집하지 않습니다. 전송 오류 시 자동 재시도하지 않고, 실행을 다시 시작하면 새 가상 이벤트를 만듭니다.

```bash
export AEGIS_COLLECTOR_TOKEN='발급받은_수집기_비밀'
python scripts/collect_auth_synthetic.py --collector-id demo-collector --port 8000
```

## 이번 검증 기록

Mac Python 3.12.2의 가상 데이터 및 임시 SQLite로 전체 회귀를 실행했습니다. 실제 루프백 서버 프로세스를 종료·재시작해 인증 실패와 성공을 서로 다른 실행에서 전송하고, 중복·신규 혼합 배치의 중복 제거와 상관 결과 유지를 확인했습니다. Chrome에서는 가상 분석가 로그인과 역순으로 도착한 4건의 인증 이벤트·상관 근거 및 실험용 BERT의 Sysmon 추론 결과 표를 확인했습니다. 브라우저에서 수집기 폐기·재발급이나 승인 버튼의 전체 흐름은 이번에 실행하지 않았고, 관련 API·회귀 테스트로 검증합니다. PII 실모델 및 Windows 실행은 미검증입니다.
