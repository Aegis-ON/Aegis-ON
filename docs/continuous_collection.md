# 지속 수집과 재시작 검증

이 문서는 로컬 합성 시연과 미검증 Windows 수집기의 실행 방법을 구분합니다. 수집기 상태는 수집기가 마지막으로 보고한 값이며 장치의 실제 온라인 상태를 보장하지 않습니다. 분석가의 승인은 실제 차단이 아닌 시뮬레이션입니다.

## 합성 이벤트 수집기

`scripts/collect_synthetic.py`는 이 저장소의 가상 `data/demo_sysmon.json`만 읽고 Sysmon 이벤트를 하나씩 시차를 두고 전송합니다. 목적지는 실행 중인 로컬 서버의 `127.0.0.1`로만 제한됩니다. 실사용 로그를 입력받지 않으며 모델 추론 여부는 서버 설정을 따릅니다. 다음 명령에서 서버는 별도 터미널에서 실행 중이어야 합니다.

```bash
read -rs AEGIS_COLLECTOR_TOKEN
export AEGIS_COLLECTOR_TOKEN
python scripts/collect_synthetic.py --port 8000 --collector-id pc-01 --interval 2
```

실제 토큰을 셸 명령 기록이나 저장소에 적지 말고 환경에 안전하게 설정하세요. 전송 실패 시 같은 배치 키와 본문으로 기본 10회 재시도하고 성공 응답 이후 다음 이벤트로 넘어갑니다. 재시도 대기 시간과 횟수는 `--retry-delay`와 `--retries`로 조정할 수 있습니다. 재실행은 새 배치 키를 사용하므로 서버가 이벤트 단위로 중복을 인식하는지 확인하는 데 쓸 수 있습니다. 전송이 성공한 합성 사례만 표시하며 원문과 토큰을 출력하지 않습니다. 실사용 이벤트나 실제 Windows Sysmon을 수집하는 도구가 아닙니다.

## Windows 수집기 (실제 Windows 검증 필요)

`scripts/collect_sysmon.ps1`은 Sysmon Operational 채널의 새 Event ID 1·3을 읽습니다. Sysmon 설치 및 설정을 변경하지 않으며 Event ID 3은 Sysmon 설정에서 생성되도록 활성화돼 있어야 합니다. Sysmon이 설치된 실제 Windows에서는 우선 사용자 권한과 기존 설정, 로그 보존 크기 및 Event 3 설정을 확인해야 합니다. 현재 기능의 실제 Windows 실행, PowerShell 구문과 Event Log 동작은 검증하지 못했습니다.

먼저 관제 개요의 **수집기 등록**에서 개인정보가 없는 고유 ID를 입력합니다. 서버는 수집기별 인증 정보를 한 번만 표시하며 해시만 저장합니다. 전달은 신뢰할 수 있는 안전한 경로를 사용하고, 명령줄·저장소·메신저에 비밀값을 남기지 마세요. 각 PC의 전용 Windows 계정으로 다음을 실행합니다. `InitializeCredential` 단계에서는 발급된 값을 숨겨 입력하며 같은 계정에 묶인 DPAPI 암호 파일을 만듭니다. 해당 폴더의 ACL을 해당 계정과 관리자만 접근하도록 제한하세요. 서비스 계정으로 실행한다면 해당 계정으로 파일을 준비해야 합니다.

```powershell
New-Item -ItemType Directory -Force "$env:LOCALAPPDATA\Aegis-ON" | Out-Null
.\scripts\collect_sysmon.ps1 -CollectorId 'pc-01' -CursorPath "$env:LOCALAPPDATA\Aegis-ON\cursor.txt" -CredentialPath "$env:LOCALAPPDATA\Aegis-ON\collector.secret" -InitializeCredential
.\scripts\collect_sysmon.ps1 -CollectorId 'pc-01' -CursorPath "$env:LOCALAPPDATA\Aegis-ON\cursor.txt" -CredentialPath "$env:LOCALAPPDATA\Aegis-ON\collector.secret" -ServerUrl 'https://soc.example.invalid'
```

두 번째 명령은 종료될 때까지 계속 실행됩니다. 자동 시작은 별도로 해당 계정의 Windows 작업 스케줄러나 서비스 관리자가 필요하며 이 저장소가 자동 설치하지 않습니다. 다른 PC에는 서로 다른 ID·자격 파일·커서를 사용합니다. 수집기 ID는 DB에 그대로 저장하므로 실명이나 호스트명 대신 임의 식별자를 사용하세요.

원격 연결은 신뢰할 수 있는 인증서가 있는 HTTPS와 접근 제한이 필요합니다. 서버의 TLS 종단 및 방화벽은 운영자가 구성합니다. 프록시를 사용할 때는 신뢰할 수 있는 프록시에서만 전달한 HTTPS 원본 정보를 ASGI 서버가 받아들이도록 설정하세요. 임의의 외부 `X-Forwarded-*` 헤더는 신뢰하지 마세요. HTTP는 서버와 클라이언트가 모두 같은 호스트의 loopback인 경우에만 사용할 수 있습니다. 리디렉션과 인증서 검증 우회는 지원하지 않습니다. 공유 토큰 수집은 기본 비활성이며 이전 시스템을 이행할 때만 서버에 `AEGIS_ALLOW_LEGACY_COLLECTOR_TOKEN=1`, 수집기에 `-UseLegacySharedToken`을 명시할 수 있습니다. 이 모드에서는 PC별 신원이 보장되지 않습니다.

### 기존 PC에서 인증 정보 교체

관제 화면에서 해당 수집기를 **폐기**한 후 **재발급**합니다. 기존 수집기 프로세스를 먼저 중지하고, 같은 Windows 계정에서 다음을 실행해 새 자격 파일에 일회성 비밀을 숨겨 입력합니다. 기존 자격 파일은 덮어쓰지 않습니다. 기존 커서·pending·binding을 지우거나 수정하지 마세요.

```powershell
.\scripts\collect_sysmon.ps1 -CollectorId 'pc-01' -CursorPath "$env:LOCALAPPDATA\Aegis-ON\cursor.txt" -CredentialPath "$env:LOCALAPPDATA\Aegis-ON\collector-new.secret" -InitializeCredential
.\scripts\collect_sysmon.ps1 -CollectorId 'pc-01' -CursorPath "$env:LOCALAPPDATA\Aegis-ON\cursor.txt" -CredentialPath "$env:LOCALAPPDATA\Aegis-ON\collector-new.secret" -ServerUrl 'https://soc.example.invalid'
```

ID와 서버 origin을 바꾸면 기존 커서 바인딩을 사용할 수 없습니다. 자격 변경 이전에 이미 인증된 요청은 변경 후 완료될 수 있으며 재발급된 자격으로 보고됐다는 것을 서버가 확정하지 못합니다. 새 비밀 발급 응답이 유실되면 다시 폐기한 뒤 재발급해야 합니다. 실제 Windows의 프로세스 중지, DPAPI, 재시작 및 pending 복구는 아직 검증하지 않았습니다.

처음 실행하면 현재 채널 끝에서 시작하므로 그 이전의 이벤트는 자동 수집하지 않습니다. 각 배치의 레코드 번호 범위를 `.pending`에 먼저 기록하고 서버가 분석·저장을 확인한 후에만 커서를 갱신합니다. 연결이 끊겨도 같은 범위와 배치 키를 재전송하며, 원본 이벤트가 사라졌거나 재구성한 내용이 기존 요청과 다르면 중단하거나 충돌을 반환해 확인하도록 합니다. 오류 이벤트, 인증 실패, 중복 식별자 충돌 등 서버가 4xx 오류로 배치를 거부하면 수집기는 중단합니다(429는 재시도). 운영자가 커서를 진행하지 않은 상태에서 원인을 확인하고 재처리해야 합니다. 지속된 전송 실패로 로그 보존 범위를 넘어가면 잃은 이벤트는 복구할 수 없습니다.

커서의 `.binding`은 수집기 ID와 서버 origin의 SHA-256 지문을 보관합니다. 다른 서버 또는 ID에 같은 커서를 쓰는 것을 거부하므로 설정이 바뀌면 별도 경로를 사용하고 이전 데이터의 처리 계획을 검토하세요. 기존 PR #12의 바인딩 없는 커서는 **원래 서버와 수집기 ID를 직접 확인한 후에만** `-AdoptExistingCursor`로 가져올 수 있습니다. 커서가 없는데 binding 또는 pending이 남아 있으면 자동으로 초기화하지 않고 중단합니다. 커서 파일을 지우거나 임의로 수정하면 중복 또는 누락을 초래할 수 있습니다. 커서의 번호와 지문도 민감할 수 있어 로컬 접근을 제한해야 합니다.

체크포인트 및 pending 쓰기는 전원 장애에 대한 강제 디스크 동기화를 보장하지 않습니다. 갑작스러운 전원 손실, 파일 손상 또는 수동 변경 후의 무손실 복구는 검증되지 않았으며 중단 원인과 채널 보존 범위를 확인해야 합니다.

Sysmon 로그가 삭제된 뒤 레코드 번호가 재사용되거나 롤오버가 발생한 경우 현재 범위 검사만으로 모든 초기화와 손실을 감지할 수 없습니다. 장기 중단 후 복구 가능한 범위는 Windows 이벤트 로그 보존 기간에 달려 있습니다. 동일 이벤트 판정에 필요한 ID가 없거나 충돌하는 경우 중복 여부를 안전하게 확정할 수 없습니다. 관련 DB의 해시와 가명처리된 정보도 개인정보 노출 위험이 남습니다.

수집된 Sysmon 이벤트는 수집기 ID·호스트·채널·EventRecordID에 따라 구분합니다. JSON 수집은 이벤트 단위 중복 제거가 없으며 같은 배치 키와 본문의 재전송만 중복 방지합니다. 같은 식별자의 내용이 다르면 충돌로 전체 배치를 거부합니다. 서로 다른 수집기의 이벤트는 동일 장치라고 가정해 합치지 않습니다. 기존 v1/v2 이력에는 새 이벤트별 지문이 없어 v3 이행 이전의 동일 기록을 나중에 다시 보내면 중복될 수 있습니다. 레코드 번호가 재사용되고 내용까지 동일하면 서로 다른 발생을 구분할 수 없습니다. 이 지문은 원문을 저장하지 않지만 추측 가능한 입력과 대조될 위험이 있고 현재 무기한 보존됩니다.

엔드포인트 묶음 식별자는 수집기 ID와 소문자로 정규화된 호스트명의 SHA-256 값입니다. 인증된 조회에서 사용할 수 있지만 호스트 후보를 대조하거나 이력을 연결하는 데 악용될 수 있습니다. 동명 장치, 호스트명 재사용 또는 이름 변경도 있으므로 같은 물리 장치라는 보장은 없습니다.

발신 Sysmon Event ID 3만 사용하며, 같은 수집기와 보고된 호스트 이름의 관찰에서 발생 시각 기준 10분 이내(양 끝 포함) 서로 다른 목적지 3개 이상이면 검토 경고를 만듭니다. 동일 발생 시각은 한꺼번에 처리해 임의의 이벤트 순서를 부여하지 않습니다. IPv4와 IPv4-mapped IPv6 주소는 같은 목적지로 정규화합니다. 수신 또는 방향 미상 이벤트는 집계하지 않습니다. 이 집계는 **호스트 수준**이며 연결이 동일 프로세스·출발지 또는 실제로 동일한 PC에서 왔다고 확정하지 않습니다. 여러 프로세스의 연결을 합산할 수 있으므로 원인 프로세스의 일치나 공격을 주장하지 않습니다.

연속 수집에서는 저장된 이벤트를 사용해 여러 배치와 재시작 뒤에도 분석하며, 늦게 도착한 이벤트는 발생 시각을 기준으로 해당 신규 이벤트를 포함하는 겹치는 10분 창을 재평가합니다. 기존 경고에 완전히 포함된 창은 중복 경고를 만들지 않습니다. 기존 미승인 경고의 모든 이벤트가 새 창에 포함되면 그 경고를 확장할 수 있습니다. 부분적으로만 겹치는 창은 서로 합쳐 10분을 넘기지 않고 별도 경고로 남깁니다. 승인된 경고의 시뮬레이션 승인과 당시 근거는 수정하지 않으며, 새로운 증거가 추가되면 별도의 검토 대기 경고를 만듭니다. 같은 이벤트의 재전송은 기존 수집 중복 검사를 거치고 충돌 또는 처리 실패는 배치 전체를 롤백합니다.

신규 이벤트의 발생 시각별 전후 10분 구간을 만들고 겹치는 구간만 합쳐 조회합니다. 기존 팬아웃 경고도 저장된 근거의 발생 시각을 사용해 수집기·호스트·시작 시각 인덱스로 관련 범위만 비교합니다. 이력 전체의 누적 경고 수나 크기만으로 새 수집을 차단하지 않습니다. 수신 시각을 기준으로 오래된 경고를 무시하지 않으므로 과거에 발생한 이벤트가 늦게 도착해도 해당 시점의 경고와 비교합니다.

자원 제한은 **각 조회 범위**의 이벤트 50,000개와 관련 경고 10,000개 및 해당 ID 목록 8 MiB, **한 호스트·배치**의 재평가 작업 단위 250,000과 경고 변경 1,000개입니다. 동일한 좁은 시간 범위에 이력이 밀집하면 여전히 상한에 도달할 수 있으며, 이때 일부만 저장하거나 ACK하지 않고 전체 배치를 503으로 롤백합니다. 작업 단위와 경고 변경 한도는 호스트별이며 배치 전체의 처리량 한도는 아닙니다. 기록 유실·롤오버, 다른 수집기의 중복, 호스트명 변경·동명, 로그 누락은 동일 장치 여부를 판별하지 못합니다. 정상 관리·모니터링 연결도 조건을 만족할 수 있습니다.

## 나중에 Windows에서 확인할 절차

1. 실제 기록은 저장소 밖의 비공개 장소에만 보관하고, Sysmon 서비스 및 Operational 채널 접근 권한을 확인합니다. 기존 Sysmon 설정을 덮어쓰지 않습니다.
2. Event ID 3이 수집되도록 이미 설정되어 있는지 확인합니다. 설정을 바꾸어야 한다면 적용 범위와 영향을 별도로 검토합니다.
3. 로컬 서버 또는 검증된 TLS 종단을 준비한 뒤 수집기를 실행하고 정상 프로세스와 사용자가 통제하는 정상 연결을 만듭니다. 실제 공격이나 파괴적인 명령은 실행하지 않습니다.
4. 수집 상태, 발생·수신 시각, 관련 이벤트·탐지 및 승인 시뮬레이션 이력을 확인합니다. 인증되지 않은 조회가 거부되는지도 확인합니다.
5. 서버와 수집기를 순서대로 중단하고 재시작해 ACK 전후의 재전송, 중복 여부와 보존 기간 내 복구를 확인합니다. 로그 삭제·롤오버 및 장기 중단에서는 손실이 가능한 범위를 기록합니다.

합성 데이터의 결과와 정상 로그만으로 실환경의 공격 탐지율이나 재현율을 계산하지 않습니다.

## 이벤트 전체 지문 변경 시 기존 수집 이력

이 버전부터 동일 식별자의 내용 충돌 여부는 정규화에 사용하지 않는 필드까지 포함한 이벤트 JSON 객체를 키 순서에 독립적으로 직렬화한 뒤 SHA-256 지문으로 비교합니다. 원본 객체는 저장하지 않습니다. 지문은 추측 가능한 원본과 대조될 수 있으므로 접근을 제한해야 합니다.

이전 PR #12의 v3 데이터베이스에는 정규화된 일부 필드의 지문만 저장되어 전체 원본의 일치 여부를 복원할 수 없습니다. 같은 배치 키·본문의 재시도는 기존 결과를 반환하지만, 이전 이벤트를 새로운 배치 키로 재전송하면 안전하게 일치 여부를 확인할 수 없어 409로 중단합니다. 업데이트 전 DB와 보조 파일을 백업하고, 발생하면 기존 기록과 수집기 커서·pending을 운영자가 대조해 처리하세요. 장부나 커서를 자동 삭제하거나 변경하지 마세요.
