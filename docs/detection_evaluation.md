# Aegis-ON 합성 탐지 평가

이 평가는 현재 규칙 탐지기와 휴리스틱 기준선, 발신 연결 상관분석의 **작은 합성 회귀 평가**입니다. 결과는 실제 환경의 탐지율, 공격 성공 여부, BERT 모델 성능을 입증하지 않습니다. 모델은 아직 연결되어 있지 않습니다. 평가는 로그에 들어 있는 문자열을 분석하며, 명령을 실행하거나 기록된 주소에 접속하지 않습니다.

## 실행

저장소 루트에서 Python 환경을 준비한 뒤 다음을 실행합니다.

```bash
PYTHONPATH=src python -m aegis_on.evaluation --dataset evaluation/synthetic_v1.json --split eval
```

개발용 분할은 `--split dev`를 사용합니다. 같은 데이터셋과 분할로 동일한 입력을 평가합니다. 결과를 비교할 때는 데이터셋 ID와 버전, 파일 SHA-256, 평가 대상 분할, 구현 커밋과 평가 기준을 함께 보관하세요. `dev`는 기준과 구현 점검에, `eval`은 그 결정 후 별도로 비교하는 데 사용합니다. 이 합성 `eval`을 반복해서 수정 기준으로 삼으면 그 데이터에 적합된 평가가 될 수 있습니다.

## 데이터와 정답

`evaluation/synthetic_v1.json`은 고정된 JSON manifest입니다. `schema_version`은 `1`, `dataset_id`는 `aegis-synthetic-v1`입니다. 총 43개 사례로 다음과 같이 구성합니다.

| 분할 | 이벤트 단위 명령 사례 | 배치 단위 연결 사례 | 합계 |
| --- | ---: | ---: | ---: |
| dev | 10 | 6 | 16 |
| eval | 19 | 8 | 27 |

각 사례는 `case_id`, 관련 변형을 묶는 `group_id`, `split`, `unit`, `task`, `truth`, `truth_reason`, `context`, `expected_engine_behavior`, `technique_truth`, `synthetic`, Sysmon 형태의 `events`를 갖습니다. 파일의 정답과 기대 동작 설명은 입력 이벤트 바깥에 보관합니다. 탐지기에 레이블이나 설명을 전달하지 않습니다.

- `command_behavior`는 Event ID 1 하나를 한 사례로 사용합니다. `truth`는 합성 시나리오에 적힌 맥락에서 관제자가 추가 검토할 필요가 있는지에 대한 **주관적인 주석**입니다. `positive`는 의심 사례, `negative`는 정상으로 설정한 사례, `unknown`은 정보가 부족한 사례입니다. 정상으로 설정한 PowerShell이나 해시 확인에도 규칙이 경고할 수 있습니다.
- `fanout_condition`은 한 호스트의 Event ID 3 기록 묶음을 한 사례로 사용합니다. `truth`는 **배치 안에 같은 호스트의 명시적 발신 기록으로 10분 이내 서로 다른 목적지 3개 이상이 있는지**를 나타냅니다. 양 끝 시각을 포함하고, IPv4-mapped IPv6는 대응하는 IPv4와 같은 주소로 셉니다. 수신은 발신에 포함하지 않습니다. 방향이 없는 기록 때문에 조건을 결정할 수 없다면 `unknown`입니다. 빈 기록, 오류, 미지원 사례는 파서 결과를 확인해야 합니다.
- `context`는 합성 시나리오가 설정한 정상·의심 맥락을 별도로 나타냅니다. 정상 운영 연결도 팬아웃 조건이 참이면 `truth=positive`입니다. 이 정답은 스캔이나 공격이 발생했다는 정답이 아니며, T1595 실제 기법의 정답으로 취급하지 않습니다.
- `technique_truth`는 명령 사례에서 특정 T번호에 대응하는 **독립적인 행위 후보 주석**입니다. 값이 없거나 `unknown`이면 해당 기법의 정답이 없다는 뜻입니다. 관제 `truth`가 `unknown`이어도 특정 행위 후보가 `positive` 또는 `negative`로 주석되어 있으면 그 기법의 분모에는 포함할 수 있습니다. 반대로 `truth=negative`인 정상 관리 명령에도 T1059 후보가 있을 수 있습니다.

`T1059` 후보는 명령 해석기 실행 신호이지 악성 실행의 확정이 아닙니다. Sysmon Event 1의 이미지에서 PowerShell 프로세스 생성이 관찰되면 명령줄이 없어도 T1059 후보를 양성으로 주석할 수 있지만, 구체적 명령과 의도에 대한 전체 관제 정답은 판단 불가로 유지합니다. 현재 기준선은 명령줄이 없으면 신호를 내지 않으므로 이러한 실행을 놓칠 수 있습니다. `T1105` 후보는 합성 시나리오에서 정한 원격 도구 이전 관련 명령 신호로, 실제 전송 성공의 증거가 아닙니다. `T1485`, `T1489` 후보 역시 가상 시나리오에 부여한 삭제·서비스 중지 시도에 관한 약한 연결이며 실제 파괴나 중단이 발생했다는 뜻이 아닙니다. 일반적인 `curl`, `wget`, `certutil` 사용이 모두 공격인 것은 아닙니다. 특히 로컬 `certutil -hashfile` 정상 사례는 키워드 기반 오탐 여부를 확인하기 위해 포함되어 있습니다.

`eval-python-rmtree`는 Python의 `shutil.rmtree` 명령을 가상 증거 디렉터리 삭제 시도로 주석한 의심 예제입니다. 명령은 실행하지 않으며, 텍스트만으로 악성 의도나 삭제 성공을 확인할 수 없습니다. 현재 기준선이 해당 표현을 포착하지 못하는 경우 전체 관제 과제와 파괴 후보 평가에서 누락을 관찰하기 위한 사례입니다.

MITRE ATT&CK의 기법 정의와 이 데이터의 후보 주석은 구분해야 합니다. ATT&CK는 공격자의 행동을 설명하지만, 여기의 입력은 합성 명령 문자열이나 소수의 연결 기록만 담고 있습니다. 예를 들어 셸 실행, 파일 다운로드 명령 또는 서비스 중지 문자열만으로 공격자의 의도나 명령 성공은 확인할 수 없습니다. `rm`·`del`에 의한 삭제도 덮어쓰기 여부 등에 따라 복구 가능할 수 있어, 문자열만으로 영구 파괴를 확정할 수 없습니다.

| 엔진이 사용하는 번호 | MITRE 공식 기법 | 이 평가에서 확인하는 것 |
| --- | --- | --- |
| [T1059](https://attack.mitre.org/techniques/T1059/) | Command and Scripting Interpreter | 합성 시나리오의 명령·스크립트 해석기 실행 후보 |
| [T1105](https://attack.mitre.org/techniques/T1105/) | Ingress Tool Transfer | 합성 시나리오의 원격 도구 이전 관련 명령 후보. 실제 전송 성공은 알 수 없음 |
| [T1485](https://attack.mitre.org/techniques/T1485/) | Data Destruction | 합성 시나리오에서 주석한 삭제·파괴 시도 후보. 실제 데이터 파괴는 알 수 없음 |
| [T1489](https://attack.mitre.org/techniques/T1489/) | Service Stop | 합성 시나리오에서 주석한 서비스 중지 명령 후보. 실제 중지 결과는 알 수 없음 |
| [T1595](https://attack.mitre.org/techniques/T1595/) | Active Scanning | 엔진이 팬아웃 출력에 붙이는 임시 번호. 이 데이터셋은 연결 수만으로 실제 스캔 정답을 부여하지 않음 |

`truth_reason`은 합성 시나리오의 정답 판단 근거입니다. `expected_engine_behavior`는 정답과 분리된 **현재 구현에 대한 예상**으로, 정확도 계산의 정답으로 쓰지 않습니다. 정답은 탐지기의 실제 출력에서 자동으로 생성하지 않았습니다. 다만 라벨 역시 제한된 합성 상황에 대한 작성자의 판단이며 외부 전문가 합의나 실환경 검증 결과가 아닙니다.

## 집계와 제외

- 이벤트 사례의 분모는 분석 가능한 Event ID 1 사례 수입니다. 배치 사례의 분모는 분석 가능한 독립 배치 수입니다. 배치의 연결 이벤트를 각각 별도 TP로 세지 않습니다.
- `command_behavior`에서는 해당 사례에 규칙 또는 휴리스틱 탐지가 하나라도 있으면 양성 예측으로 봅니다. `fanout_condition`에서는 상관분석 결과가 있으면 양성입니다. 이 기준은 점수 임계값을 적용하지 않습니다. 예를 들어 `eval-rmdir`에서 파괴 후보 T1485를 놓쳐도 명령 해석기 T1059가 나오면 **전체 관제 사례는 TP**가 될 수 있으므로, 이를 파괴 기법을 정확히 탐지한 것으로 읽으면 안 됩니다. 기술 후보별 결과를 함께 확인해야 합니다.
- 동일 사례에서 규칙과 기준선이 같은 기술 후보를 각각 내더라도 사례·기법 조합의 한 예측으로 취급해야 합니다. 출처별 결과는 별도로 구분해 비교합니다.
- 각 지표에는 평가 단위, 양성/음성 support, TP·FP·FN·TN, precision·recall·F1과 제외 건수를 함께 봅니다. precision, recall 또는 F1의 분모가 0이면 `null` 또는 `N/A`로 표시하며 정확히 0으로 바꾸지 않습니다.
- 사례의 관제 `truth=unknown`은 관제 TP/FP/FN/TN에 넣지 않습니다. 해당 사례에 명시된 개별 `technique_truth`가 알려져 있다면 **별도의 기법 후보 분모**에는 포함할 수 있습니다. 관제 지표와 기법 후보 지표의 분모를 합치지 않습니다.
- 입력이 `invalid` 또는 `unsupported`이면 미탐으로 처리하지 않고 오류·미지원 및 제외 건수를 표시합니다. 명령 과제에 Event ID 3이 들어오거나 팬아웃 배치에 Event ID 1이 섞이는 등 과제에 맞지 않는 지원 이벤트도 이유와 함께 제외합니다. 일부 오류가 있는 배치는 남은 이벤트로 팬아웃을 계산한 값을 전체 배치의 정답과 비교하지 않습니다.
- `event_ids`는 입력 이벤트와 위치를 바탕으로 만들어지는 불투명한 결정적 식별자입니다. 보고서의 `input_event_refs`가 이를 입력 인덱스와 연결합니다. 탐지기에 사례 ID나 레이블이 노출되지 않으며, 무작위 파서 ID나 처리 순서에 따라 정답이 바뀌어서는 안 됩니다.

CLI는 JSON을 표준 출력으로 반환합니다. `tasks`에는 과제별 `overall`, `by_source`, `by_context`, 제외 건수와 정상 맥락 사례의 탐지 목록이 있고, `techniques`에는 주석된 기술 후보별 지표와 제외 건수가 있습니다. `cases`에는 사례별 정답·예측·오류와 입력 인덱스에 연결된 결정적 이벤트 ID가 포함됩니다. 결과를 파일로 저장하려면 명령에 `--output 결과파일.json`을 추가할 수 있습니다.

예를 들어, `eval-mapped`의 세 연결에는 `192.0.2.1`, `::ffff:192.0.2.1`, `192.0.2.2`가 있습니다. 첫 두 표기는 같은 주소이므로 조건 정답은 음성입니다. `eval-mapped-three`는 여기에 세 번째 고유 주소가 추가되어 조건 정답이 양성입니다. `dev-outbound-unknown`은 세 번째 방향이 없어 조건을 확정하지 못하므로 점수에서 제외합니다.

## 실행 결과 예시

다음은 현재 엔진으로 합성 `eval` 분할을 실행한 결과입니다. 기준 데이터 파일의 SHA-256은 `8339971eea84dfa61f5aa5ca60aea8ed277db468858fc80d5b3aab85dcfc8d92`입니다. 소수점 넷째 자리까지 표시했습니다.

| 평가 과제 | 평가 사례 | TP | FP | TN | FN | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 명령 관제 판단 | 16 | 9 | 4 | 2 | 1 | 0.6923 | 0.9000 | 0.7826 |
| 발신 연결 팬아웃 조건 | 6 | 3 | 0 | 3 | 0 | 1.0000 | 1.0000 | 1.0000 |

명령 평가에서는 입력 오류·미지원 2건과 정답 판단 불가 1건, 팬아웃 평가에서는 입력 오류 1건과 정답 판단 불가 1건을 각각 제외했습니다. 팬아웃의 1.0은 **여섯 개 합성 배치에서 명시한 연결 조건**을 판정한 결과로, 실제 스캔이나 공격의 탐지율이 아닙니다. 개별 기법 후보의 결과와 분모는 CLI 출력의 `techniques`에서 별도로 확인하세요.

개발용 분할의 T1059 후보는 주석된 5개 중 TP 3, TN 1, FN 1로 재현율이 0.75입니다. FN은 명령줄이 없는 PowerShell 생성 사례이며 전체 관제 점수에서는 판단 불가로 제외됩니다. 개발용 T1489에는 주석된 양성 사례가 없어 재현율은 `null`입니다.

## 분할과 품질 검사

관련 명령 변형 또는 같은 경계 실험은 사람이 지정한 동일 `group_id`로 묶어 하나의 분할에만 넣었습니다. `curl`·`wget`의 다운로드·문서 조회, `sc`·PowerShell의 서비스 중지·조회, 세 목적지 연결 사례는 각각 같은 그룹으로 eval에 배치했습니다. 시간 경계 변형은 함께 dev에 배치했습니다. 자동 검사는 group_id 중복 분할, 공백·대소문자를 정규화한 정확히 동일한 명령의 분할 간 중복, JSON 필드 순서를 정규화한 정확히 동일한 이벤트 해시의 분할 간 중복을 확인합니다. 알려진 유사 시나리오 그룹도 회귀 테스트로 확인합니다. 주소는 테스트용 IPv4·IPv6 대역만 사용합니다.

이 자동 검사는 **의미가 같은 다른 명령이나 유사한 템플릿, 동일 공격 흐름의 변형까지 완전히 찾아내지 못합니다.** 예를 들어 서로 다른 도구로 파일을 가져오는 사례와 유사한 팬아웃 템플릿은 양 분할에 여전히 존재합니다. 그룹 지정과 정답 근거는 수동 검토가 필요합니다. 이 데이터는 개발 중 eval 결과를 확인하고 재배치했으므로 독립적인 미공개 홀드아웃이 아닙니다. 향후 모델의 최종 성능은 별도 수집하고 그룹을 분리한 미사용 평가셋으로 측정해야 합니다.

데이터 형식과 분할, 레이블 균형, 알려진 입력 오류, 객관적 팬아웃 조건을 검사하려면 다음을 실행합니다.

```bash
PYTHONPATH=src python -m unittest discover -s tests -p test_evaluation_dataset.py -v
```

## 이후 모델·실환경 평가

추후 BERT 기반 모델을 연결하면 같은 관측 입력, 같은 사례 단위와 고정 eval 분할에서 현재 기준선과 별도로 비교합니다. 학습·전처리·임계값 선택에 eval을 사용하지 않고, train/dev/eval을 사건·템플릿 가족 단위로 분리해야 합니다. 현재 manifest에는 `dev`와 `eval`만 있으므로 모델 학습에 그대로 쓰는 대신 별도의 학습 데이터와 누출 검사가 필요합니다.

이 43개 합성 사례는 적고 작성자의 가정에 좌우됩니다. 소수 사례의 지표 변동이 크며 실제 네트워크·업무 환경, 탐지 지연, 사용자별 편향이나 공격 일반화를 대표하지 않습니다. 실환경 성능은 사용 권한과 레이블 근거가 확보된 독립 데이터로 별도 검증해야 합니다. 개인정보 탐지·가명처리 품질은 본 탐지 평가의 점수가 아니며 별도의 데이터와 평가가 필요합니다.
